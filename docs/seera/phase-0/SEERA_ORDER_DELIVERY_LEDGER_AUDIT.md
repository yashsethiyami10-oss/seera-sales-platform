# Seera Order, Delivery and Ledger Audit

## Order architecture

Three separate order concepts exist: consumer `Order`, Sales/commerce extensions around it, and institutional `BusinessOrder`. None safely represents all Seera flows today. `BusinessOrder` is the closest candidate because it has organisation key, source, owner, territory, totals and lifecycle timestamps, but buyer/seller/fulfilment/billing/delivery parties and independent approval/payment/fulfilment states are incomplete. Its item stores ordered quantity and price/tax totals, not accepted, allocated, dispatched, delivered, refused, returned and cancelled quantity histories.

Recommendation: one governed channel-order aggregate with explicit order type (`SECONDARY`, `DISTRIBUTOR_REPLENISHMENT`, `ASSISTED_DISTRIBUTOR`, `PRIMARY`), party roles, attribution snapshots, price/scheme/tax snapshots and independent state machines. Decide in design whether this additively generalises `BusinessOrder` or is a new aggregate; do not modify storefront Order into a channel ledger.

## Required event model

Immutable item events must record quantity, value basis, reason, actor/membership/partner, location/evidence, occurred/recorded time and reversal linkage. Derived balances must reject over-delivery and negative quantities. Header status is a projection only. Reassignment must not rewrite historical salesperson/distributor/territory attribution.

Delivery outcomes and evidence (partial, refusal, shop closed, payment issue, unavailable stock, damage, reschedule, receiver/OTP/signature/image/invoice/GPS) are not fully represented. Existing Shipment/ShipmentEvent and commerce dispatch are carrier/header oriented. Add item delivery attempts and proofs, private asset authorization and immutable outcome history.

## Pricing/quotation

Existing quotation versioning, approvals, PDF and pricing rules are reusable. Missing are organisation catalog isolation, four channel price levels, pack/case conversions, effective price lists, schemes/free goods, territory/group eligibility, special-discount limits and immutable scheme snapshots. Separate Seera branding, sequence, tax registration and storage are mandatory; template fallback must fail closed.

## Ledger verdict

Do not build a parallel Seera ledger. Enterprise Finance already contains balanced journals, immutable ledger entries generated by posting, reversal, AR invoices/receipts/allocations, AP, banking reconciliation, credit/debit notes, expenses, ageing/collections and idempotent event logs. Reuse it after real tenant context and party-account mappings.

Running balance should be computed/projected from postings rather than stored as an editable truth. A customer/order total is never a ledger. Corrections use reversal/counter-entry. Distributor/retailer disputes require an additive case/evidence/status workflow without mutating posted entries.

## Payment verification gap

Storefront Razorpay verification is unrelated to the required bank-proof process. Build `PaymentProof` (UTR, bank, amount/date, payer party, references, private asset, submitter), `PaymentVerification` (pending/accepted/partially matched/rejected, maker-checker, reason), and allocations linked to Finance receipts/reconciliation. Duplicate UTR policy must be organisation+bank scoped with controlled exceptions. Upload never sets paid; only verified posted/allocated finance events influence release.

## Performance truth

No current report can reliably compute required net delivered quantity/value. Add a versioned read model sourced from item events. Returns count only when approved/effective; reversals counter prior events. Tests must cover partial delivery, refusal, return, cancellation, duplicate event, out-of-order sync and attribution retention.
