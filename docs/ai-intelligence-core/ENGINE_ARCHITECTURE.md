# MUV AI Intelligence Core™ — Engine Architecture

> Every layer addresses all 15 required dimensions. Where a layer maps to a real, already-built
> Module (1-9), dimensions describing *current* behavior are grounded in that Module's own
> documentation and code — never re-invented. New-work dimensions describe only what genuinely
> does not exist today. No layer below is application code; every "Internal Logic" description
> is a specification, not an implementation.

---

# Layer 1 — Knowledge Integration

- **Purpose:** Bring the four Knowledge Factories' content into a form the existing platform's
  Module 1 (Knowledge Foundation) and V4 governance layer can store, version, and later retrieve
  — without modifying either's existing schema in a breaking way.
- **Responsibilities:** Ingest each Factory's `knowledge_objects.json`/`KNOWLEDGE_OBJECTS.md`
  content; assign each Knowledge Object a stable identity inside Module 1's model; preserve
  Evidence Classification (Verified/Derived/Founder Decision Required, per Founder Intelligence
  KF Constitution Article 12) as a first-class field, not lost metadata; never ingest a Gap
  Record as if it were retrievable fact.
- **Inputs:** `docs/knowledge-factory/products/*` (Product KF), `docs/marketing-knowledge-
  factory/domains/*` (Marketing KF), `docs/institutional-sales-knowledge-factory/*`,
  `docs/founder-intelligence-knowledge-factory/*` — all four read-only.
- **Outputs:** New `KnowledgeItem`/`KnowledgeVersion` rows (Module 1) or `CanonicalSourceDocument`
  rows (V4 governance layer) per Knowledge Object, tagged with a new `sourceFactory` provenance
  value and the original KOID preserved as an external reference.
- **Dependencies:** None (pipeline-opening layer).
- **Relationships:** feeds Layer 2 (Knowledge Graph) and Layer 3 (Retrieval Engine).
- **Execution Flow:** Factory content (already frozen/complete Markdown+JSON) → per-Factory
  adapter reads `knowledge_objects.json` → maps each KO's 12-field schema onto Module 1's
  `KnowledgeItem`/`KnowledgeVersion` shape (title=`name`, layer=derived from evidenceClassification,
  content=`purpose`+`scope`+prose body, provenance=KOID+repository) → writes one
  `KnowledgeVersion` per KO at `DRAFT` status → staff review promotes to `PUBLISHED` (reusing
  Module 1's existing 3-state status model unmodified).
- **Internal Logic:** A **new, additive field**, `sourceFactory` (enum: `PRODUCT_KF` |
  `MARKETING_KF` | `INSTITUTIONAL_SALES_KF` | `FOUNDER_INTELLIGENCE_KF`), is required on
  `KnowledgeItem` — Module 1's `KnowledgeFileType` enum is closed and does not include these
  values (confirmed by direct schema inspection); adding a new enum value is additive, not
  breaking, matching the precedent Module 5's own later sprints already set (`operational-data-
  adapter.ts`, `orchestration-plan.ts` both extended coverage by adding new *values*, never by
  redefining an existing field's meaning). Evidence Classification maps to `KnowledgeLayer`
  loosely (Founder Note/Verified → treat as `INTERNAL`-or-`PUBLIC` depending on the KO's own
  domain, Derived Founder Principle → `INTERNAL`, Founder Decision Required → **never ingested
  as retrievable content at all**, only as a queryable "known gap" record — this is the single
  most important rule in this layer).
- **Edge Cases:** A Knowledge Object superseded by a later Founder Decision inside its own
  repository (e.g., a future amendment to a frozen Marketing KF domain) — ingestion must re-run
  per-Factory, not attempt incremental diffing in v1. A KO whose `evidenceClassification` is
  ambiguous or missing — reject ingestion for that KO, log it, never guess a layer.
- **Failure Modes:** A Factory's JSON schema drifts from what the adapter expects (e.g., a future
  fifth Factory uses a different field name) → adapter must fail loudly per-item, not silently
  skip or partially ingest. A duplicate KOID ingested twice → second ingestion must be a
  no-op/update, never a duplicate row (Zero Duplicate Knowledge, applied at the storage layer
  now, not just the authoring layer).
- **Recovery Strategy:** Ingestion is idempotent and re-runnable in full from the frozen source
  files at any time — since all four Factories are themselves the durable source of truth, no
  ingested row is ever "lost" in a way that can't be regenerated by re-running ingestion.
- **Validation Rules:** Every ingested row must be traceable back to exactly one KOID in exactly
  one Factory; a Founder-Decision-Required KO must never appear in a query result set intended
  for customer-facing retrieval (Layer 3 must filter this, and Layer 1 must tag it so Layer 3
  can).
- **Acceptance Criteria:** 100% of Verified/Derived KOs across all four Factories ingestible
  without schema-breaking changes to Module 1; 0% of Founder-Decision-Required KOs retrievable
  as if they were answered fact.
- **Founder Constraints:** Never modify a frozen Factory's own files to make ingestion easier —
  the adapter conforms to the Factory's existing shape, not the reverse (per every Factory's own
  binding "read-only" status).
- **Future Scalability:** A fifth future Factory needs only a new `sourceFactory` enum value and
  a new adapter function — the storage shape (`KnowledgeItem`/`KnowledgeVersion`) does not
  change per Factory added.

# Layer 2 — Knowledge Graph

- **Purpose:** Represent the *relationships* between Knowledge Objects — both the relationships
  already recorded inside each Factory's own `RELATIONSHIPS.md`/`relationships.json`, and the
  new cross-Factory relationships that only become visible once all four Factories sit in one
  system.
- **Responsibilities:** Preserve every intra-Factory relationship type already defined (`feeds`,
  `citationOnly`, `relatesTo`, `closestAnalog`, `provenance`, etc. — each Factory already uses a
  slightly different vocabulary, honestly, not unified retroactively); add a new cross-Factory
  edge type where none exists today (e.g., Founder Intelligence KF's `KO-FD-MI-001` citing
  Marketing KF's `KO-PM-CH2-009` is already a real edge in Founder Intelligence KF's own
  `relationships.json` — this layer's job is to make that edge queryable at runtime, not to
  invent new ones).
- **Inputs:** Layer 1's ingested `KnowledgeItem` rows; every Factory's own `relationships.json`
  (already-structured, machine-readable).
- **Outputs:** A queryable graph structure (node = KnowledgeItem, edge = typed relationship) —
  this document specifies the shape, not the storage technology (graph DB vs. adjacency table in
  Postgres is an implementation choice for developers, explicitly out of scope here per "do not
  implement models").
- **Dependencies:** Layer 1.
- **Relationships:** feeds Layer 3 (a retrieval query can traverse the graph, not just keyword-
  match) and Layer 8 (Conflict Resolution needs to know which KOs relate to which before it can
  detect a conflict between them).
- **Execution Flow:** Each Factory's `relationships.json` is parsed at ingestion time (Layer 1) →
  edges are written using the *already-declared* `from`/`to`/`type` triples, unmodified → a
  reverse index is built so "what relates to KO-X" is a single lookup, not a scan.
- **Internal Logic:** **No existing module in the 9-module platform builds anything like this.**
  The closest real precedent is `lib/retrieval/relationships.ts` (Module 5) — its exact current
  scope was not independently re-verified line-by-line in this design pass and should be checked
  by developers before assuming it's a blank slate; if it already models simple product-to-
  product relationships, this layer extends that shape rather than replacing it, per Reference
  Before Create.
- **Edge Cases:** A relationship that only makes sense within one Factory (e.g., Domain 6's
  internal `governs` chain) should not be surfaced as a cross-Factory edge — edge *scope*
  (intra-Factory vs. cross-Factory) must be preserved, not flattened.
- **Failure Modes:** A relationship references a KOID that failed Layer 1 ingestion (e.g., a Gap
  Record's cross-reference) — the edge must still exist for graph completeness (a Gap Record IS
  part of the graph) but must be flagged as pointing to non-retrievable content.
- **Recovery Strategy:** Same as Layer 1 — fully re-derivable from the frozen source files.
- **Validation Rules:** Every edge in the graph must correspond to a real entry in some Factory's
  own `relationships.json` — this layer never infers a new relationship that no Factory
  document actually states (this would be invention, forbidden under every Factory's own
  Constitution/governance).
- **Acceptance Criteria:** 100% of declared relationships across all four Factories represented
  as queryable edges; 0% invented edges.
- **Founder Constraints:** This layer is descriptive of existing declared relationships, never
  a place to add new editorial judgment about how content "should" relate.
- **Future Scalability:** Graph traversal depth and cross-Factory edge density will grow with
  each new Factory; this design does not assume a fixed graph size.

# Layer 3 — Retrieval Engine

- **Purpose:** Extend the real, already-implemented Module 5 (Knowledge Retrieval Core) so it
  can serve the four new Factories alongside its existing four sources, without breaking its
  existing contract.
- **Responsibilities:** Everything Module 5 already does (find/filter/rank/return, read-only,
  deterministic keyword matching, permission-layer filtering) — reused unmodified — plus serving
  the four new source types.
- **Inputs:** A query (customer message, staff query, or another engine's structured request);
  Layer 1's ingested content; Layer 2's graph (for relationship-aware retrieval, new capability).
- **Outputs:** `RetrievalResult[]`, matching Module 5's existing shape.
- **Dependencies:** Layer 1, Layer 2.
- **Relationships:** feeds Layer 4 (Context Engine) exactly as Module 5 already feeds Module 6.
- **Execution Flow:** Unchanged from Module 5's existing 8-stage pipeline
  (`retrieval-pipeline.md`) — query in, permission-filtered ranked results out.
- **Internal Logic — the concrete integration decision:** Module 5's `RetrievalResult.sourceType`
  is a **closed union of exactly four values** (`KNOWLEDGE | PRODUCT_INTELLIGENCE |
  PROBLEM_INTELLIGENCE | CARE_INTELLIGENCE`), confirmed directly in `lib/retrieval/sources.ts`.
  Two precedents already exist for extending coverage without redefining this field: (a) map new
  content to `sourceType: "KNOWLEDGE"` with a new `relationship` value carrying the real
  distinction (the pattern `operational-data-adapter.ts` and `orchestration-plan.ts` both already
  use for `CUSTOMER_INTELLIGENCE`/`VARIANT`/`CATEGORY` content), or (b) formally extend the
  union with four new values (`MARKETING_KF | INSTITUTIONAL_SALES_KF | FOUNDER_INTELLIGENCE_KF`
  — `PRODUCT_KF` content already partially overlaps `PRODUCT_INTELLIGENCE`, requiring an explicit
  developer decision on whether Product KF content should merge into the existing
  `PRODUCT_INTELLIGENCE` type or get its own). **This document recommends option (a)** — it is
  the lower-risk, already-proven pattern, and keeps Module 5's original contract fully backward
  compatible — but names both explicitly since the final choice is an implementation decision,
  not this document's to make.
- **Edge Cases:** A query that should return a Founder-Decision-Required Gap Record (e.g., a
  staff member specifically asking "what don't we know about X") — Module 5's existing
  permission-layer filtering model does not have a concept of "gap visibility"; this needs a new,
  explicit filter dimension, not a repurposing of `PUBLIC`/`INTERNAL`/`CONFIDENTIAL`.
- **Failure Modes:** Same as Module 5's own documented failure modes, extended: a malformed
  cross-Factory reference in retrieved content (Layer 2 edge to non-ingested content) must
  degrade to "relationship exists, target not retrievable" rather than error.
- **Recovery Strategy:** Read-only layer, same as Module 5 — no write-path failure to recover
  from.
- **Validation Rules:** Retrieval must never return a Gap Record's content as if it were an
  answered fact (this is the runtime enforcement of Layer 1's ingestion-time rule).
- **Acceptance Criteria:** All four new source types retrievable through the *same* 8 server
  actions Module 5 already exposes — no new action surface required for basic retrieval.
- **Founder Constraints:** Module 5's explicit non-goals remain non-goals here too — this layer
  does not become semantic/vector search by extension (that remains the V4 governance layer's
  `embedding-service.ts` territory, separately).
- **Future Scalability:** The `relationship`-value workaround (option a) scales to an unbounded
  number of future source types without further `sourceType` union growth.

# Layer 4 — Context Engine

- **Purpose:** Extend Module 6's real Context Engine to carry Marketing/Institutional Sales/
  Founder Intelligence signal, using fields that already exist but are currently unused.
- **Responsibilities:** Everything Module 6's Context Engine already does (assemble
  `IntelligenceContext` from retrieved knowledge, customer goal, referenced products/care
  workflows) — reused unmodified — plus populating the two currently-opaque pass-through fields.
- **Inputs:** Layer 3's `RetrievalResult[]`; session state (Module 8).
- **Outputs:** `IntelligenceContext`, Module 6's existing shape, with `businessContext`/
  `institutionalContext` now populated instead of empty.
- **Dependencies:** Layer 3.
- **Relationships:** feeds Layer 5 (Reasoning Engine) exactly as Module 6's Context Engine
  already feeds its own downstream engines.
- **Execution Flow:** Unchanged from Module 6's existing internal flow — this layer only changes
  *what* populates two already-declared fields, not the flow itself.
- **Internal Logic:** `businessContext`/`institutionalContext`/`websiteContext` exist today as
  opaque `Record<string, unknown>` fields that only the Priority Engine checks for
  presence/absence, never contents (confirmed directly from Module 6's code). This layer defines
  their first real shape: `businessContext` carries Founder Business/Optimization/KPI Intelligence
  signal relevant to the query (e.g., "this is a pricing question — apply Revenue Quality
  reasoning," per Founder Intelligence KF `KO-FD-BU-003`); `institutionalContext` carries
  Institutional Sales KF signal (e.g., qualification-stage awareness per `KO-IS-002`) when the
  session is flagged as an institutional buyer conversation.
- **Edge Cases:** A consumer session with no institutional signal at all — `institutionalContext`
  stays empty exactly as it does today; this is not a regression, it's the correct default.
- **Failure Modes:** Populating these fields with malformed data must not break the Priority
  Engine's existing presence/absence check — the new content must be additive-safe by
  construction (any well-formed object satisfies "is present").
- **Recovery Strategy:** Stateless per-request assembly — no persistence to recover.
- **Validation Rules:** The Context Engine's existing consumers (Priority, EQ, CQ, Decision) must
  continue to function unmodified if these two fields are absent — backward compatibility is a
  hard requirement, not a nice-to-have.
- **Acceptance Criteria:** An institutional-buyer session demonstrably carries different
  `institutionalContext` than a retail session; a founder-facing/internal query demonstrably
  carries `businessContext` grounded in Founder Intelligence KF reasoning.
- **Founder Constraints:** This layer must never let `businessContext`/`institutionalContext`
  smuggle in content that should have gone through Layer 3's retrieval/permission filtering —
  it assembles, it does not bypass retrieval's own gates.
- **Future Scalability:** A future fifth Factory's context signal would use the same
  opaque-field pattern, or, if it recurs enough, earn its own named field — matching Founder
  Intelligence KF's own Article 8 (Formalize a Pattern Only After It Proves Itself).

# Layer 5 — Reasoning Engine

- **Purpose:** Ground Module 6's existing Priority/EQ/CQ synthesis logic in Founder Intelligence
  KF's evidenced reasoning frameworks, rather than leaving each engine's fixed rule tables
  disconnected from *why* those rules are the right ones.
- **Responsibilities:** Everything Priority/EQ/CQ Engines already do (deterministic scoring
  against fixed lexicons/tables) — reused unmodified — plus an explicit, documented tie between
  each engine's rule table and the Founder Intelligence KF reasoning KO that justifies it.
- **Inputs:** Layer 4's `IntelligenceContext`.
- **Outputs:** `PriorityResult`, `EQResult`, `CQResult` — Module 6's existing shapes, unchanged.
- **Dependencies:** Layer 4.
- **Relationships:** feeds Layer 6 (Decision Engine) exactly as today.
- **Execution Flow:** Unchanged — this layer is a documentation/justification layer over
  existing deterministic logic, not a new execution path.
- **Internal Logic:** Concrete example of the tie this layer establishes: Module 6's CQ Engine's
  care-scoring logic should be traceable to Founder Intelligence KF's `KO-FD-PH-003` (Darshan
  Test: Movement/Trust/Memory/Execution/Identity) and `KO-FD-SI-001` (Qualification-Before-
  Presentation) — not because the code changes, but because a developer or auditor asking "why
  does the CQ Engine weigh this signal this way" now has a real, evidenced answer instead of an
  opaque rule table. This is documentation-as-architecture, explicitly permitted since "design
  the architecture, do not implement" does not forbid specifying *why* a deterministic rule
  should exist.
- **Edge Cases:** Where an existing engine's rule table has no clean Founder Intelligence KF
  analog (e.g., a purely operational scoring weight) — this is stated honestly as "engineering
  convention, not Founder-reasoning-derived," not force-fit to a citation that doesn't really
  apply.
- **Failure Modes:** None new — this layer does not change runtime behavior.
- **Recovery Strategy:** N/A (documentation layer).
- **Validation Rules:** Every claimed tie between an existing rule and a Founder Intelligence KF
  KOID must be independently checkable against that KO's actual content — no citation invented
  for the sake of appearing grounded.
- **Acceptance Criteria:** Every one of Module 6's Priority/EQ/CQ rule categories has either an
  explicit Founder Intelligence KF citation or an explicit "engineering convention" label — no
  unlabeled rule.
- **Founder Constraints:** This layer must never be used to justify changing an existing rule's
  actual behavior without a real Founder Decision — grounding a rule in evidence is not the same
  as authority to modify it.
- **Future Scalability:** As Founder Intelligence KF's own Gap Records (`KO-FD-GAP-001`,
  `KO-FD-GAP-002`) receive Founder Decisions, this layer's citations should be revisited, not
  left stale.

# Layer 6 — Decision Engine

- **Purpose:** Extend Module 6's real Decision Engine's fixed action cascade minimally so it can
  weigh signal from the four new Factories, without redesigning its already-working synthesis
  logic.
- **Responsibilities:** Everything the Decision Engine already does (`buildDecision(priority,
  context, memory, eq, cq)` → fixed cascade: escalate → care workflow → share knowledge → ask
  clarifying question, with confidence from an 8-point evidence-count model) — reused unmodified
  — plus recognizing when a business/institutional-sales-relevant recommendation is warranted.
- **Inputs:** `PriorityResult`, `IntelligenceContext`, `MemoryResolution`, `EQResult`, `CQResult`
  — Module 6's existing five inputs, unchanged.
- **Outputs:** `DecisionPackage` — Module 6's existing shape.
- **Dependencies:** Layer 5.
- **Relationships:** feeds Layer 7 (Memory), Layer 9 (Confidence is computed alongside, not
  after), and downstream to Layer 11 via Module 7.
- **Execution Flow:** Unchanged first-match-wins cascade; this layer's only addition is a
  *new candidate outcome* in the existing cascade — not a new cascade shape.
- **Internal Logic:** Today's cascade recognizes escalation, care-workflow, knowledge-sharing,
  and clarifying-question outcomes. This layer specifies a fifth candidate — **recommend
  institutional-sales handoff** — inserted into the existing cascade at the same priority
  position a care-workflow recommendation occupies today, triggered when `institutionalContext`
  (Layer 4) is populated and evidence strength meets the existing confidence bar. This is
  additive to the cascade, not a replacement of its ordering logic.
- **Edge Cases:** A session with both a care-workflow need and institutional-sales-handoff
  signal simultaneously — the existing cascade's first-match-wins ordering already resolves this
  class of ambiguity; this layer inherits that resolution order rather than inventing a new
  tie-breaking rule.
- **Failure Modes:** Same as Module 6's existing failure modes — degrades to "ask clarifying
  question," never to a fabricated recommendation, per the existing design's own discipline.
- **Recovery Strategy:** Stateless per-request; no persistence to recover.
- **Validation Rules:** The new institutional-sales-handoff outcome must never fire on
  `businessContext`/`institutionalContext` alone without corroborating evidence from Layer 3
  retrieval — mirrors the existing rule that no outcome fires on a single weak signal.
- **Acceptance Criteria:** The five-outcome cascade (four existing + one new) demonstrably
  produces the same outputs as today's four-outcome cascade for every existing test case, plus
  correctly fires the new outcome only when `institutionalContext` and supporting evidence are
  both present.
- **Founder Constraints:** Per Founder Intelligence KF Constitution Article 7 (Change Only What
  Was Authorized) — this layer changes the cascade's candidate set, not its confidence formula,
  its five-input contract, or any of Module 6's other engines.
- **Future Scalability:** A future Marketing-specific or Founder-specific outcome would follow
  the same additive-insertion pattern established here.

# Layer 7 — Memory Engine

- **Purpose:** Reuse Module 6's Memory Resolver and Module 8's `ExperienceSession` largely as-is
  — this is the layer with the least genuinely new work, since session-level memory already
  exists and is live in production.
- **Responsibilities:** Everything Memory Resolver + `ExperienceSession` already do (expiration/
  layer-filtered memory resolution, accumulated conversation memory across a session) — reused
  unmodified.
- **Inputs:** Session identity (Module 8); prior turns within the session.
- **Outputs:** `MemoryResolution` — Module 6's existing shape.
- **Dependencies:** None beyond what Module 6/8 already require.
- **Relationships:** feeds Layer 6 (Decision Engine) exactly as today.
- **Execution Flow:** Unchanged.
- **Internal Logic:** The one genuinely new consideration: should a customer's *institutional
  buyer status* or *Founder-facing staff status* persist across sessions (long-term memory),
  not just within one (short-term, `ExperienceSession`)? Module 6's README explicitly states "no
  long-term storage" for Memory Resolver — this document does not propose changing that; it
  names the open question honestly rather than deciding it, since it is a data-retention and
  privacy decision, not an architecture-design one.
- **Edge Cases:** Same as today's — a session that expires mid-conversation, a customer who
  returns after expiration with no memory carried forward. Unchanged behavior.
- **Failure Modes:** Same as today's documented failure modes.
- **Recovery Strategy:** Same as today's — `ExperienceSession` is the durable record; Memory
  Resolver itself holds nothing durable to recover.
- **Validation Rules:** Unchanged from Module 6/8's existing validation.
- **Acceptance Criteria:** No regression to existing session-memory behavior; the open
  long-term-memory question is explicitly logged as a Founder Decision candidate in
  `FOUNDER_REVIEW.md`, not silently decided either way.
- **Founder Constraints:** Do not introduce long-term cross-session memory without an explicit
  Founder Decision — this is a real privacy/PII-retention question (per the earlier platform
  audit's own Section 12 finding: no dedicated PII redaction/anonymization layer exists anywhere
  in this codebase today).
- **Future Scalability:** If long-term memory is later authorized, it should be a new, explicit
  model — not an quiet extension of `ExperienceSession`'s current session-scoped shape.

# Layer 8 — Conflict Resolution Engine

- **Purpose:** Detect and resolve cases where two of the four Factories (or a Factory and the
  existing Modules 1-4) give different guidance on the same question — the layer this entire
  integration effort most needed and had the least existing coverage for.
- **Responsibilities:** Detect a conflict at retrieval or reasoning time; classify its severity;
  apply a resolution rule where one exists; escalate honestly where none does.
- **Inputs:** Layer 3's retrieved results (when more than one source answers the same query);
  Layer 2's graph (to know which KOs are even comparable).
- **Outputs:** Either a resolved, single answer with its resolution rationale attached, or an
  explicit "unresolved conflict" flag that Layer 6 must treat as a reason to escalate, never to
  guess.
- **Dependencies:** Layer 2, Layer 3.
- **Relationships:** feeds Layer 6 (Decision Engine) and Layer 9 (Confidence Engine — an
  unresolved conflict must lower confidence, never be silently averaged away).
- **Execution Flow:** Retrieval returns candidates from ≥2 sources → conflict detector checks
  whether they agree → if they agree or one is a strict specialization of the other (e.g.,
  Institutional Sales KF citing Marketing KF as its own provenance — not a conflict, a citation)
  → pass through → if they genuinely disagree → apply resolution rule → if no rule applies →
  flag unresolved.
- **Internal Logic — this is the layer that directly answers Founder Intelligence KF's own
  `KO-FD-GAP-002` (Gap Record: Cross-Repository Conflict Arbitration).** That Gap Record states
  plainly: *"if the Marketing Knowledge Factory and this Founder Intelligence Knowledge Factory
  ever imply different guidance on the same reasoning question, which governs? No Founder
  decision on this has been made... a plausible-sounding precedence rule invented here would
  itself violate Constitution Article 3."* This engineering document **does not resolve that
  question either** — inventing a precedence rule here would repeat the exact mistake Founder
  Intelligence KF's own Article 3 forbids, just one layer down the stack. What this layer
  *does* specify: the **mechanism** for detecting and surfacing a conflict (so the question is
  visible at runtime, not silently buried), reusing the V4 governance layer's existing
  `KnowledgeConflict` model as the closest real precedent for conflict *representation* (though
  that model was built for source-ingestion-time conflicts, not cross-Factory runtime conflicts
  — a real, disclosed scope difference, not an assumed fit).
- **Edge Cases:** Two sources agree on substance but use different terminology (e.g., Marketing
  KF's "customer" vs. Institutional Sales KF's "institutional account") — not a conflict, a
  vocabulary difference; the detector must distinguish substance disagreement from vocabulary
  difference, or it will over-flag.
- **Failure Modes:** Over-flagging (every minor phrasing difference treated as a conflict) makes
  the system unusable; under-flagging (real disagreements passed through silently) is worse and
  violates the entire ecosystem's Never-Invent discipline by proxy. This document names the
  failure mode explicitly rather than picking a threshold, since tuning that threshold is an
  implementation/testing decision.
- **Recovery Strategy:** An unresolved conflict is not an error state — it is a valid, expected
  output that Layer 6 must handle as its own cascade branch (escalate).
- **Validation Rules:** No conflict may be auto-resolved by "the newer repository wins" or "the
  more specific repository wins" defaults, per the Gap Record's own explicit warning against
  inventing precedence — every auto-resolution rule this layer ever applies must trace to an
  actual Founder Decision, not a convenient default.
- **Acceptance Criteria:** 100% of detected cross-Factory disagreements either resolved via an
  explicit, Founder-approved rule or surfaced as an unresolved-conflict flag — 0% silently
  merged or averaged.
- **Founder Constraints:** This is the one layer in the entire architecture whose correct,
  complete design is **blocked on a Founder Decision** (per `KO-FD-GAP-002`) — this document
  specifies the mechanism, not the missing arbitration rule, and says so plainly rather than
  guessing.
- **Future Scalability:** Once a real precedence rule is authorized, it plugs into this layer's
  "apply resolution rule" step without changing the detection mechanism around it.

# Layer 9 — Confidence Engine

- **Purpose:** Extend Module 6's real Confidence Engine's evidence-count model to correctly
  weigh the four new source types, and to reflect Layer 8's conflict signal.
- **Responsibilities:** Everything the Confidence Engine already does (evidence-count scoring
  against a max of 8) — reused unmodified — plus two new inputs: source-type diversity and
  unresolved-conflict penalty.
- **Inputs:** Evidence used by the Decision Engine (Module 6's existing input); Layer 8's
  conflict-detection result (new input).
- **Outputs:** A confidence score — Module 6's existing shape, unchanged range/format.
- **Dependencies:** Layer 6, Layer 8.
- **Relationships:** feeds Layer 11 (a low-confidence answer must be assembled differently —
  more hedged, more likely to route to escalation).
- **Execution Flow:** Unchanged core scoring; one new pre-step (check Layer 8's flag) and one
  new consideration (does the evidence span multiple independent sources, or one repeated
  source restated).
- **Internal Logic:** An unresolved Layer 8 conflict must cap confidence below whatever
  threshold the existing system treats as "answerable without hedging" — the exact numeric
  threshold is an implementation/tuning decision, not specified here, but the *rule* (a real,
  unresolved cross-Factory disagreement can never coexist with high confidence) is a hard
  architectural requirement, directly following from Founder Intelligence KF Constitution
  Article 4 (Evidence Proportional to Claim).
- **Edge Cases:** All four new source types agreeing independently on the same answer should
  score *higher* confidence than one source alone repeated (an actual improvement over today's
  four-source model, since it previously could only ever see up to four independent sources,
  now up to eight).
- **Failure Modes:** Same as today's — a confidence score is never itself customer-facing text;
  it is an internal signal Layer 11 consumes.
- **Recovery Strategy:** Stateless, recomputed per request.
- **Validation Rules:** Confidence must never be computed from a Gap Record's mere presence
  (a Gap Record is evidence of *absence*, not supporting evidence for an answer) — this is the
  runtime enforcement of Layer 1's ingestion-time exclusion rule, reinforced at the Confidence
  layer specifically because this is the layer most likely to accidentally treat "we have a
  record about this" as "we have evidence for this."
- **Acceptance Criteria:** Confidence scoring backward-compatible with all existing four-source
  test cases; demonstrably lower on any case with an unresolved Layer 8 conflict.
- **Founder Constraints:** No confidence threshold change here is itself the arbitration rule
  Layer 8 is blocked on — this layer only specifies that conflict *lowers* confidence, not by
  how much, avoiding the same invented-precedence trap.
- **Future Scalability:** The evidence-count ceiling (currently 8, sized for 4 sources) should
  scale proportionally as future Factories are added — an explicit implementation note, not a
  design decision made here.

# Layer 10 — Care Engine

- **Purpose:** Extend Module 4 (Care Intelligence Foundation) and Module 6's CQ Engine to close
  the Institutional Sales gap Module 4's own documentation already discloses.
- **Responsibilities:** Everything CIF + CQ Engine already do (care workflows, escalation logic,
  service standards, care-quotient scoring) — reused unmodified — plus the institutional-
  sales-specific fields CIF's own known-limitations.md names as missing.
- **Inputs:** Layer 4's `IntelligenceContext` (including the now-populated `institutionalContext`,
  Layer 4); Layer 3's retrieved Care/Institutional Sales content.
- **Outputs:** `CQResult` (Module 6's existing shape) plus, new, an institutional-care-fields
  object when relevant.
- **Dependencies:** Layer 4, Layer 3.
- **Relationships:** feeds Layer 6 (Decision Engine) exactly as CQ already does.
- **Execution Flow:** Unchanged CQ scoring flow; the new institutional-care-fields object is
  assembled alongside it, not instead of it.
- **Internal Logic — grounded in an already-disclosed gap, not a newly-discovered one:** Module
  4's own known-limitations.md states directly: *"Institutional Sales support is structural, not
  operational"* — CIF can represent an institutional workflow via free-text `category`/
  `applicableCustomerSegments` fields, but has no dedicated fields for minimum order quantity,
  credit terms, or similar institutional-specific care needs, and its own authors call this
  *"new schema for a future module, not a gap in this one."* This layer is that future module.
  New fields specified: `minimumOrderQuantity`, `creditTermsReference` (a reference, never a
  live credit decision — that remains a commercial/finance system's authority, per the same
  separation-of-concerns discipline Product KF's `FR-001` established for pricing), and
  `institutionalEscalationPath` (distinct from CIF's existing general escalation logic, since an
  institutional account's escalation contact is often a named account owner, not a generic
  support queue).
- **Edge Cases:** A retail customer session must never see institutional-care fields populated —
  this is gated by the same `institutionalContext` presence check Layer 4/6 already use.
- **Failure Modes:** Missing institutional-care data for a flagged institutional session must
  degrade to CIF's existing generic care workflow, never block the response entirely.
- **Recovery Strategy:** Same as CIF's existing model — stateless per-request assembly from
  versioned, published Care Intelligence content.
- **Validation Rules:** Institutional-care fields must only ever be populated from Institutional
  Sales KF-sourced content (Layer 1's provenance tag) — never inferred or defaulted.
- **Acceptance Criteria:** An institutional-buyer session with relevant Institutional Sales KF
  content available produces a `CQResult` that includes the new institutional-care fields; a
  retail session's `CQResult` is byte-for-byte unchanged from today's.
- **Founder Constraints:** This layer does not grant institutional customers credit or
  commercial terms — it surfaces *reference* information for a human to act on, per Institutional
  Sales KF's own `KO-IS-002`'s (Qualification) and this ecosystem-wide Never-Promise-Unauthorized
  discipline (Founder Intelligence KF `KO-FD-SI-002`).
- **Future Scalability:** Additional institutional-care fields can be added the same way,
  provided each is sourced from real Institutional Sales KF content, not invented to fill a
  perceived gap.

# Layer 11 — Response Assembly Engine

- **Purpose:** Turn Module 7's `ResponseBlueprint` (a structural instruction set with **no
  customer-readable prose today**) into actual response content — this is the single largest
  genuine architecture gap in the entire platform, larger than the Knowledge Factory integration
  problem this protocol specifically asked about.
- **Responsibilities:** Everything Module 7's Response Composer + Module 8's Response
  Model/Website Channel Adapter already do (build the structural blueprint: intent, tone words,
  ordered structure outline, restrictions; adapt it for the Website channel; apply the small
  fixed `CUSTOMER_MESSAGE_BY_ACTION` lookup table for non-generative responses) — reused
  unmodified — plus the missing generative step.
- **Inputs:** `ResponseBlueprint` (Module 7); Layer 9's confidence score; Layer 8's conflict
  status.
- **Outputs:** Customer-facing response content — today, only ever a fixed lookup-table string;
  this layer specifies what a generative step would need to produce the same, given a richer
  blueprint.
- **Dependencies:** Layer 6, Layer 9, Layer 10.
- **Relationships:** feeds Layer 12 (Tool Orchestration, when the response requires an action)
  and Module 8's delivery mechanism.
- **Execution Flow:** Unchanged for the deterministic path (fixed action → fixed lookup-table
  response, e.g., `ESCALATE` → a fixed escalation message). **New path specified, not built:**
  for actions where the fixed lookup table is too rigid (e.g., `ANSWER_CUSTOMER` with retrieved
  knowledge that varies per query), a generative step consumes the `ResponseBlueprint`'s
  structure outline + restrictions + the actual retrieved knowledge content (Layer 3) and
  produces prose — explicitly, per this protocol's own instruction, **this document does not
  select a model or write integration code for this step.**
- **Internal Logic:** The `ResponseBlueprint`'s existing `restrictions` field (per Module 7's own
  design) is the exact mechanism that must carry every constraint this whole ecosystem has
  established: never state a price/stock/policy fact without a live lookup (Product KF `FR-001`);
  never invent a claim beyond approved wording (Marketing KF's Claim Discipline, `KO-PM-CH2-008`,
  cited by Founder Intelligence KF `KO-FD-MI-002`); never present a Gap Record's absence as an
  answer (this ecosystem's master meta-rule, Founder Intelligence KF `KO-FD-AG-002`). A future
  generative step's prompt-construction is out of scope for this document, but its **guardrails**
  are in scope, because guardrails are architecture, not implementation.
- **Edge Cases:** Low Layer 9 confidence + no Layer 8 conflict → hedge language required, not
  refusal. Low confidence + unresolved conflict → the response must route to escalation
  (Layer 6's existing cascade), never attempt to generate a confident-sounding answer over an
  unresolved disagreement.
- **Failure Modes:** A generative step that ignores its `restrictions` field is the single
  highest-consequence failure mode in this entire architecture — this document specifies that
  restrictions must be enforced *after* generation too (a post-generation validation pass
  checking the output doesn't contain an unauthorized price/claim/fabricated fact), not only
  trusted as a prompt instruction, mirroring this codebase's own "never trust the client,
  re-derive server-side" discipline (confirmed as the single most consistent theme in the
  existing platform audit) applied to model output instead of client input.
- **Recovery Strategy:** If the generative step fails or times out, fall back to Module 7's
  existing fixed lookup-table response for the given action — never fall back to silence or a
  raw error.
- **Validation Rules:** Every generated response must be traceable to the `ResponseBlueprint`
  and retrieved knowledge that produced it (explainability, extending Module 6's existing
  `explainability.md` pattern to this new layer).
- **Acceptance Criteria:** Deterministic-path responses (today's fixed lookup table) remain
  100% unchanged; a generative path, once implemented by developers, must pass a post-generation
  restrictions check before delivery, with 0% tolerance for restriction violations reaching a
  customer.
- **Founder Constraints:** No AI model is selected, no prompt is written, no API is implemented
  here — per the protocol's own explicit instruction. This document specifies the contract a
  future generative step must honor, not the step itself.
- **Future Scalability:** The same `ResponseBlueprint`-to-generation contract should extend to
  future channels (WhatsApp, Email — explicitly not built by Module 8 today) without a new
  contract per channel.

# Layer 12 — Tool Orchestration Engine

- **Purpose:** Specify how the AI would invoke real system capabilities (order status lookup,
  live escalation ticket creation, etc.) beyond what Module 7's fixed 9-action cascade already
  covers, since Module 7's own docs explicitly name integrations (order system, chat UI, tool
  calling) as "later integrations this module does not build."
- **Responsibilities:** Map each of Module 7's 9 existing action types to whether it requires a
  real system call (a "tool") or is purely conversational; specify the tool-call contract for
  the ones that do, reusing existing Server Action patterns rather than inventing a new
  integration style.
- **Inputs:** Module 7's `ExecutionPackage` (specifically, the chosen action).
- **Outputs:** A tool-call request/result pair, or nothing (for purely conversational actions).
- **Dependencies:** Layer 6, Layer 11.
- **Relationships:** feeds back into Layer 7 (Memory) once a tool result is known, and Layer 11
  (a tool result may need to be woven into the final response).
- **Execution Flow:** Action selected (Module 7) → is this a tool-requiring action?
  (`RECOMMEND_PRODUCT` may need a live stock/price check per Product KF `FR-001`'s own rule that
  these fields are never static; `ESCALATE` needs a real ticket/handoff creation, not just a
  message) → if yes, call the tool via the existing Server Action convention → attach result to
  the response assembly step (Layer 11).
- **Internal Logic:** **Reuse, do not reinvent, the codebase's own established integration
  pattern.** The platform audit already confirms the correct shape: every mutation goes through
  a `"use server"` action that independently self-enforces RBAC and validates via Zod (the same
  convention every other domain in this codebase already follows, per `CLAUDE.md`'s own
  documented architecture) — a "tool" in this architecture is simply an existing or new Server
  Action, called server-side, never exposed as a client-callable model function. No new
  client-side API surface is introduced by this layer.
- **Edge Cases:** A tool call fails mid-response (e.g., stock lookup times out) — the response
  must degrade to "let me confirm and get back to you," per this ecosystem's own established
  escalation-over-fabrication discipline, never present stale or guessed data as live.
- **Failure Modes:** A tool call that silently uses cached/stale data instead of a genuine live
  lookup would violate Product KF's `FR-001`/`FR-006` directly — this is named as an explicit
  forbidden failure mode, not merely an edge case to handle gracefully.
- **Recovery Strategy:** Tool calls are independently retriable/re-callable — no tool call
  result is assumed durable across a retry.
- **Validation Rules:** A tool call must only ever touch data the calling session's own RBAC
  already permits (no new privilege-escalation path introduced by "the AI asked for it").
- **Acceptance Criteria:** Every one of Module 7's 9 action types has an explicit tool-
  requirement classification (yes/no) and, for "yes," a named target Server Action (existing or
  to-be-built) — no action left unclassified.
- **Founder Constraints:** No new API route is introduced where a Server Action already
  suffices, per this codebase's own CSRF-protection rationale for preferring Server Actions
  (documented in `CLAUDE.md`).
- **Future Scalability:** A future WhatsApp/Email channel (Module 8's own named gap) would reuse
  the same tool-call contract, with only the channel adapter differing.

# Layer 13 — Continuous Learning Architecture

- **Purpose:** Close the loop from Module 8's real but partial feedback capture back to the
  Knowledge Factories and the reasoning engines — the largest genuine gap in the entire
  platform, since nothing today updates any Factory or engine based on real usage.
- **Responsibilities:** Capture what already exists (Module 8's `ExperienceFeedback`, `feedback-
  capture.ts`, `review-preparer.ts` — staff-facing review prep) — reused unmodified — plus
  specify how a reviewed, approved learning becomes a new Knowledge Object or a Gap Record
  resolution, following this ecosystem's own established Rejected-Approaches and Decision-Record
  patterns rather than inventing a new learning format.
- **Inputs:** `ExperienceFeedback`; staff review outcomes (Module 8's `review-preparer.ts`);
  Layer 8's logged unresolved conflicts (a real signal about where the knowledge base itself
  needs Founder attention).
- **Outputs:** A structured learning record — this document specifies its shape, grounded in
  Founder Intelligence KF `KO-FD-LN-002`'s ten-field Decision Record pattern (Decision ID,
  Scope, Authority/date, Question, Evidence, Alternatives, Status, Rationale, Conditions,
  Effect) — reused directly rather than inventing a new record format for AI-specific learning.
- **Dependencies:** Everything upstream (this is the pipeline's terminal layer).
- **Relationships:** feeds back to Layer 1 (a Founder-approved learning becomes a new ingestible
  Knowledge Object) and Layer 8 (a resolved conflict updates the conflict log).
- **Execution Flow:** Feedback captured (Module 8, today) → staff review (Module 8's existing
  `review-preparer.ts`) → **new step:** reviewed-and-approved learning is recorded as a Decision
  Record (per `KO-FD-LN-002`'s shape) → **new step:** if the learning implies a correction to an
  existing Knowledge Object, or an answer to an open Gap Record, this is routed back to the
  *owning Factory's own governance process* (a Founder Decision / Knowledge Change Request,
  exactly as every Factory's own Constitution already requires) — **this architecture explicitly
  does not let a runtime feedback loop silently rewrite a frozen Factory's content.** That would
  violate every single frozen repository's own amendment discipline (Product KF `CONSTITUTION.md`
  Article 6; Founder Intelligence KF Constitution Article 13) at exactly the layer most tempted
  to bypass it for convenience.
- **Internal Logic:** This is the direct architectural instantiation of Founder Intelligence KF's
  own Learning Engine reasoning (`KO-FD-LN-001` Rejected-Approaches-as-Institutional-Memory,
  `KO-FD-LN-002` Decision-Record-Driven Learning) — the newest Knowledge Factory in the ecosystem
  turns out to already contain the exact reasoning this layer needed, discovered rather than
  invented.
- **Edge Cases:** A pattern of repeated low-confidence answers on the same topic (a real,
  aggregable signal from Layer 9 over time) should surface as a candidate Gap Record for Founder
  review, mirroring how Marketing KF's own `KO-SC-CH2-005` treats a repeated objection as
  "commercial intelligence" — the same reasoning pattern, applied to AI-answer confidence
  instead of sales objections.
- **Failure Modes:** A learning record with no clear Authority/date/Status (per the ten-field
  model) must never be treated as authoritative — incomplete records are logged as `research
  required` status, never silently promoted.
- **Recovery Strategy:** N/A — this is itself the recovery/improvement mechanism for the rest of
  the architecture.
- **Validation Rules:** No learning record may modify a frozen Factory directly — only the
  Factory's own governance process (external to this Intelligence Core) can do that; this layer
  only ever *proposes*.
- **Acceptance Criteria:** Every piece of captured feedback either reaches a terminal reviewed
  state (approved-and-routed, rejected-with-reason per `KO-FD-LN-001`'s honesty discipline, or
  deferred) — none left permanently unreviewed by construction.
- **Founder Constraints:** This layer's proposals are never self-executing — every Factory
  update this layer ever recommends requires the same explicit Founder authorization every other
  amendment in this ecosystem has required, without exception.
- **Future Scalability:** As more Factories and more real usage accumulate, this layer's volume
  of proposed learnings will grow — its design does not assume a fixed review throughput, but
  this document does not propose automating the review step itself, since that would remove the
  human authorization this whole ecosystem's Constitution architecture depends on.
